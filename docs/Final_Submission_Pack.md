# Part 1 — Report content (drop into IEEE template)

Use the official IEEE conference template

## 1.1 Abstract (~180 words)

Reading research papers is time-consuming, and the volume of new
publications makes triage hard for both new and established researchers.
We built a cloud-native platform that lets users search open-access
academic repositories, retrieve full-text PDFs, and obtain structured
summaries — covering objectives, methodology, results, limitations, and
contributions — generated by a large language model (LLM). On top of the
summary, the platform also supports retrieval-augmented question
answering against the paper's content, similarity-based discovery of
related papers in the user's library, and an interactive knowledge graph
that visualizes entities and relationships extracted from the summary.
The system is built on Amazon Web Services using a serverless,
event-driven architecture: Cognito for user identity, CloudFront and S3
for the static frontend, API Gateway and Lambda for the synchronous API,
an SQS-triggered Step Functions state machine that orchestrates a
five-stage map-reduce summarization pipeline backed by Amazon Bedrock,
and DynamoDB single-table storage for both relational state and chunk
embeddings. The deployed system summarizes a typical academic paper
end-to-end in 27–44 seconds at an average cost of $0.20 per summary,
with idle cost of zero.

## 1.2 Problem Statement

The number of academic papers published each year continues to grow:
arXiv alone now indexes over 2.4 million preprints, and the rate of
submission has nearly doubled in the past decade. Researchers,
practitioners, and students therefore face a triage problem — given a
research question, which subset of the literature is worth reading in
full? Existing solutions partially address this: search engines surface
relevant titles and abstracts, citation graphs reveal influence, and
generic LLM chatbots can summarize text on request. None, however,
provide an end-to-end workflow that combines authenticated multi-source
search, automated full-text retrieval, structured paper-level
summarization tied to user accounts, and the cost discipline required
for sustained academic use.

## 1.3 Motivation

The motivation is twofold. First, a structured five-section summary
(Objectives / Methodology / Results / Limitations / Contributions) more
closely matches how researchers internally evaluate a paper than a
free-form prose summary; producing this consistently is exactly the
kind of repetitive cognitive task that generative AI can offload at
scale. Second, the engineering challenge — long-running asynchronous
LLM calls, parallel chunk processing, fault-tolerant orchestration, and
cost control — is itself a useful exercise in modern cloud-native
design. Building this platform forced us to make concrete decisions on
serverless compute boundaries, queue versus state-machine
orchestration, single-table NoSQL data modeling, and observability — all
core to the cloud computing curriculum.

## 1.4 Existing Solutions

We identified four classes of existing solution and articulate where
each falls short.

**Search engines (Google Scholar, Semantic Scholar, arXiv search)** are
strong at surfacing relevant papers but provide no summarization. They
return titles and abstracts; the user must still read the full text.

**Generic chat-based LLMs (ChatGPT, Claude.ai)** can summarize a paper
when given the text, but the user must manually upload or paste it.
Outputs are unstructured and not stored, so there is no cumulative
benefit from repeated use; cost is paid per query and no per-user
quota mechanism exists.

**Paper-specific tools (SciSpace, Elicit, Scite Assistant)** are the
closest competitors. They offer summarization and Q&A, but they are
proprietary SaaS with opaque cost models; they do not allow
infrastructure-level customization; and they primarily target
deep-pocketed institutional users.

**Self-hosted summarization scripts (Hugging Face pipelines, LangChain
templates)** require the user to provision and manage the entire
infrastructure themselves. They lack authentication, persistence,
search, and any operational layer.

Our platform sits in the gap: it combines authenticated multi-source
search, structured summarization, persistent per-user history,
content-level deduplication, per-user quota, full observability, and
reproducible cloud deployment — all delivered as a buildable
open-source class project that fits inside the AWS free tier for idle
operation.

## 1.5 System Architecture

The system is organized as twelve Lambda-backed microservices, three
managed data stores, two managed queues, and an event-driven
orchestrator, all provisioned reproducibly via AWS Cloud Development
Kit (CDK) in TypeScript. Figure 1 shows the deployed topology.

```
                ┌───────── End User browser ─────────┐
                │                                    │
                ▼                                    ▼
          Route 53 → CloudFront ───── (cached) ── S3 (frontend)
                          │
                          │  /v1/* dynamic API requests
                          ▼
                    API Gateway (REST)
                          │  Cognito JWT Authorizer
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
       searchFn   submitJobFn   getSummaryFn / listSummariesFn / getQuotaFn
            │         │
       arXiv +     DynamoDB
       Semantic    (write JOB)
       Scholar           │
                         ▼
                    SQS Jobs Queue ──────── DLQ (after 3 failures)
                         │
                         ▼
                  Trigger Lambda
                         │
                         ▼
       Step Functions State Machine
        ┌────────────┬─────────────┬──────────────┬────────────────┐
        ▼            ▼             ▼              ▼                ▼
   FetchPDF → ExtractText → Chunk → MapSummarize (×N parallel) → ReduceSummary
        │            │             │              │                │
        ▼            ▼             ▼              ▼                ▼
       S3        S3 text       S3 chunks       Bedrock         DynamoDB
                                              (Qwen 3 / Claude)
```

The platform is decomposed by lifecycle:

### 1.5.1 Edge layer

* **Amazon Route 53** resolves the application domain.
* **Amazon CloudFront** terminates TLS, caches the static frontend at
  edge, and serves dynamic API requests through to API Gateway. We use
  a CloudFront Function on the viewer-request event to rewrite
  directory-style URLs (e.g. `/signup/`) to their S3 keys
  (`/signup/index.html`), and to map every dynamic
  `/app/summary/<id>/` URL to a single pre-rendered placeholder, with
  the React component reading the actual id from `window.location` at
  runtime. This avoids the cost of a server-side rendering layer while
  preserving deep-linkability.

**Why CloudFront over direct S3 hosting?** S3 cannot terminate TLS on a
custom domain, has no edge caching, and provides no DDoS protection.
CloudFront delivers all three at no additional fixed cost (Price Class
100 keeps us in US/EU edges to remain free-tier eligible).

### 1.5.2 Authentication layer

* **Amazon Cognito User Pool** manages signup, email verification,
  login, and JWT issuance. The web client uses Secure Remote Password
  (SRP) so passwords are never transmitted in plaintext.

**Why Cognito + JWT at API Gateway?** API Gateway natively understands
Cognito JWTs through its built-in authorizer, so unauthenticated
requests are rejected before any Lambda runs — saving compute and
removing one class of security mistake. The alternative (per-Lambda
auth check) duplicates code and creates a path where unauthenticated
requests still warm Lambdas.

### 1.5.3 Synchronous API layer

* **Amazon API Gateway (REST)** with a Cognito JWT Authorizer.
* **Six handler Lambdas** (Node.js 20): `searchFn`, `submitJobFn`,
  `getSummaryFn`, `listSummariesFn`, `getQuotaFn`, `healthFn`. Each is
  a single-purpose microservice with its own minimal IAM role.

**Why a fleet of small Lambdas instead of one monolith?** Smaller blast
radius (a bug in one handler doesn't break others), independent
scaling, faster cold-starts, and least-privilege IAM scoped to the
specific operations each function performs.

### 1.5.4 Asynchronous summarization pipeline

* **Amazon SQS Jobs Queue** decouples the synchronous API response from
  the long-running pipeline. `submitJobFn` returns HTTP 202 with a
  `jobId` in under 200ms while the job processes in the background.
* **Dead Letter Queue (DLQ)** with `maxReceiveCount=3`: messages that
  fail processing three times move to the DLQ rather than retrying
  forever; a CloudWatch alarm fires on DLQ depth > 0.
* **AWS Step Functions** state machine orchestrates the five pipeline
  stages with declarative retries, error catching, and a `Map` state
  for parallel chunk summarization.

The pipeline:

1. **FetchPDF** — downloads the paper from its source (e.g., arXiv) to
   S3.
2. **ExtractText** — parses the PDF using the `pdf-parse` library,
   normalizes whitespace, and writes plain text to S3.
3. **Chunk** — splits the text into overlapping ~6,000-character chunks
   on paragraph boundaries, with a 400-character overlap for context
   continuity. The chunks are written to S3 (one file per chunk).
4. **MapSummarize** — Step Functions Map state with `maxConcurrency=5`
   fans out chunk summarization in parallel. Each iteration invokes
   Bedrock with a system prompt that requests structured JSON output
   covering objectives, methodology, results, limitations, and
   contributions for that chunk.
5. **ReduceSummary** — consolidates the per-chunk JSON arrays into a
   single paper-level summary via a second Bedrock call, deduplicating
   near-identical bullets and extracting 3–7 keywords. The final
   summary is written to DynamoDB; job status is set to `done` with a
   measured duration.

A separate `MarkFailed` state catches any uncaught error from any
state, captures the cause string, and updates the DynamoDB job record
to `status="failed"` with the error message — ensuring the user always
sees an honest status rather than a stuck "running" job.

**Why Step Functions instead of one big Lambda?** A single Lambda has
a 15-minute hard timeout. A 30-page paper that needs ten parallel
chunk summarizations and one reduction can exceed this. Step Functions
externalizes retries (so we don't re-run successful steps), provides a
visual execution graph for debugging, and supports parallel `Map`
states natively.

**Why pass S3 keys, not text, between states?** Step Functions limits
state input/output to 256 KB per state. A 40-page paper's extracted
text easily exceeds this. We store all heavy data in S3 and thread
only S3 keys through the state machine.

### 1.5.5 Data layer

* **Amazon DynamoDB** with a single-table design.
  * Partition key `PK = USER#{userId}`, sort key `SK` with prefixes
    `PROFILE#`, `JOB#{jobId}`, etc.
  * **GSI1** keyed on `GSI1PK = PAPER#{paperId}` enables the
    cross-user content-hash dedup feature: before submitting a new
    job, `submitJobFn` checks whether any user has already summarized
    this paper to `done` status, and if so, copies the existing
    sections+keywords into a new job record for the requesting user
    instead of consuming Bedrock tokens.
  * Billing mode `PAY_PER_REQUEST` so cost scales with traffic and
    falls to zero at idle.
* **Two S3 buckets**: one for the static Next.js frontend (private,
  served only via CloudFront with Origin Access Control), and one for
  raw PDFs / extracted text / chunks (private, with a 30-day → IA →
  90-day expiry lifecycle).

**Why DynamoDB over a relational database?** Our access patterns are
narrow: list jobs for a user, get one job by id, find any completed
summary for a paper. All can be served by partition+sort key access
patterns plus one GSI; we never need joins. DynamoDB scales without
provisioning, has no idle cost on PAY_PER_REQUEST, and provides
single-digit-millisecond reads. A relational database would introduce
both idle cost (RDS minimum) and operational burden (provisioning,
backups, version upgrades).

**Why single-table design?** The canonical DynamoDB pattern. It avoids
fan-out queries across many tables, keeps related entities co-located
on the same partition for fast retrieval, and minimizes the surface
area of indexes we have to maintain.

### 1.5.6 LLM layer

* **Amazon Bedrock** is the LLM surface. Our `lib/bedrock.ts` helper
  supports both the Anthropic Messages API format (Claude models) and
  the OpenAI-compatible Chat Completions format (Qwen, DeepSeek,
  gpt-oss). The current production model is **Qwen 3 Next 80B**
  (`qwen.qwen3-next-80b-a3b`); switching to Claude Sonnet 4.5 is a
  one-line environment variable change and pending the Anthropic
  use-case-details form approval on our AWS account.

**Why Bedrock instead of a direct LLM provider?** Authentication is
IAM-based — our Lambdas assume a role permitted to invoke Bedrock; no
external API key exists to store, rotate, or accidentally leak.
Observability is automatic: invocations appear in CloudWatch metrics
without instrumentation. Cost appears on the same AWS bill as the rest
of the platform. Finally, model swapping is centralized: changing
`BEDROCK_MODEL_ID` updates every pipeline Lambda simultaneously.

In addition to text generation, the Chunk pipeline step embeds each
chunk with **Titan Text Embeddings v2** (1024-dimensional, normalized)
and persists the vectors in DynamoDB. These embeddings power three
downstream features (Section 1.5.7).

### 1.5.7 Retrieval features (RAG, related papers, knowledge graph)

Three user-facing capabilities build directly on the chunk embeddings.

* **Talk-to-PDF chat** (`POST /chat`). Embeds the user's question with
  Titan, computes cosine similarity against the paper's chunk vectors
  (brute force; <15 vectors per paper), retrieves the top-3, and
  prompts the chat model under "answer only from the excerpts, cite by
  number" rules. The frontend renders `[N]` markers in the response as
  hoverable tooltips showing chunk index, cosine score, and snippet.
* **Related papers** (`GET /summaries/{id}/related`). Computes the mean
  of a paper's chunk embeddings (lazily filled and persisted on the JOB
  record), then ranks all the user's other DONE summaries by cosine
  similarity. Returns the top-3 above a 0.25 floor.
* **Knowledge graph** (`GET /summaries/{id}/graph`). Feeds the
  structured summary back into the LLM with a strict JSON-schema prompt
  asking for typed entities (method, dataset, metric, task, concept,
  result) and typed relationships (uses, achieves, extends,
  evaluated_on, introduces, cites, compares_with). The output is
  sanitized (drop dangling edges, dedupe ids, clamp counts) and cached
  on the JOB record. The frontend renders it with React Flow using a
  dagre left-to-right layout. Each node card shows the LLM-generated
  summary inline; the four most-connected entities surface as a "key
  concepts" rail above the canvas. A `?force=1` query param skips the
  cache for regeneration.

### 1.5.8 Operational layer

* **CloudWatch Logs** — structured JSON, one log group per Lambda,
  retention 7 days.
* **Four CloudWatch Alarms** wired to an SNS topic with email
  subscription: DLQ depth > 0, Step Functions failed executions,
  pipeline Lambda errors > 3 in 5 min, API Lambda errors > 5 in 5 min.
* **CloudWatch Dashboard** with seven widgets covering executions,
  durations, request counts, latency P95, queue depths, and per-Lambda
  invocations and errors.
* **AWS X-Ray** with active tracing on all eleven Lambdas and the Step
  Functions state machine, providing distributed traces from API
  Gateway through Lambda to Bedrock.
* **AWS Budgets** alarm at $50 / month with notifications at 80%
  actual and 100% forecasted spend.
* **GitHub Actions CI** runs `npm run lint` and `npm run build` on
  every pull request; future work would add ephemeral PR environments.

### 1.5.9 How the architecture satisfies the rubric criteria

**Scalability.** Lambda autoscales to several thousand concurrent
executions per region, throttled centrally by reserved concurrency if
needed. DynamoDB on PAY_PER_REQUEST handles spikes without
provisioning. SQS scales to unbounded queue depth. Step Functions Map
states fan out parallel chunk summarization with `maxConcurrency=5`,
deliberately capped to stay under our Bedrock model TPS quota.
CloudFront caches static assets at hundreds of edges globally.

**Reliability.** Every cross-service interaction has an explicit
failure path: Step Functions retries with exponential backoff per
state, SQS DLQ with a 3-attempt threshold, idempotent Lambda handlers,
CloudWatch alarms wired to SNS, multi-AZ via every managed service we
use. Failed jobs are surfaced to the user with the specific error
cause, not a black-box "running forever" state.

**Latency.** P95 search latency is under 1.5 s end-to-end. P95 summary
completion for papers up to 30 pages is 27–44 s; chunk summarization is
parallelized so wall-clock latency is dominated by the longest single
chunk plus the reduction. CloudFront edge caching reduces frontend
asset latency to single-digit milliseconds for repeat visitors. Cold
Lambda starts on Node 20 are sub-second.

**Data storage.** DynamoDB single-table design with one GSI; PAY_PER_REQUEST
billing; encrypted at rest with AWS-managed keys. S3 PDFs bucket has a
lifecycle policy (30-day transition to Infrequent Access, 90-day
expiry). Frontend bucket is private, accessible only through
CloudFront Origin Access Control. All buckets block public access by
default.

**Data pipeline.** The summarization pipeline is a textbook
fan-out/fan-in event-driven dataflow: SQS triggers a single state
machine execution per submission, the Map state fans out parallel
Bedrock invocations, the reduce state fans them back in. Heavy data
(PDFs, extracted text, chunks) is kept in S3 with only keys passed
through the state machine to stay under the 256 KB state-payload limit.

**Microservices design pattern.** Each Lambda has one job, its own
log group, its own IAM role, its own bundling unit, and communicates
with peers exclusively via SQS messages, Step Functions transitions,
or DynamoDB items — never direct Lambda-to-Lambda invocations. CDK
stacks correspond to bounded contexts (Auth, Data, Pipeline, Api,
Frontend, Ops), each independently deployable.

## 1.6 Implementation Details (optional subsection if space permits)

The frontend is Next.js 14 with `output: 'export'` for fully static
hosting. We use Tailwind CSS for styling, the Geist font family for
typography, and a small custom toast component (no third-party UI
library) for ergonomics. Authentication state is persisted via the
`amazon-cognito-identity-js` library; sessions survive page refresh
because we read the cached session via the synchronous
`getSignInUserSession` API.

Backend Lambdas are bundled with esbuild (via CDK's
`NodejsFunction` construct) so each function ships a single
minified `.js` plus its required dependencies, achieving sub-100ms
cold starts. The pipeline LLM calls go through a thin
`bedrock.ts` helper that supports both Anthropic and OpenAI-compatible
APIs, with retry-with-backoff on throttling exceptions.

Search runs against arXiv and Semantic Scholar in parallel
(`Promise.allSettled`), merging by arXiv ID, DOI, then normalized
title. A regex-quoted phrase boost on the title field ensures that
multi-word queries (e.g., "attention is all you need") return the
exact paper rather than every paper containing any of those words.

## 1.8 Future Work

Talk-to-PDF chat, related-papers discovery, and the knowledge graph
have all shipped on top of the original MVP. The natural next
extensions, in priority order:

* **Side-by-side PDF reader** — Render the original PDF alongside the
  summary using `pdfjs-dist`, with hover-to-jump from each summary
  bullet to its source chunk in the PDF.
* **Comparative analysis** — Submit two or three papers, receive a
  unified table comparing methodology, results, and limitations across
  them.
* **Streaming chat answers** — Token-by-token streaming via Lambda
  Function URLs (API Gateway does not support response streaming).
* **Multi-region disaster recovery** — DynamoDB Global Tables and S3
  cross-region replication with documented RTO and RPO.
* **Containerized PDF extraction** — Replace `pdf-parse` with Grobid
  running in Fargate for higher-quality structured extraction (proper
  bibliography parsing, section detection).
* **Anthropic Claude swap-in** — `bedrock.ts` already supports the
  Anthropic API format; once the use-case-details form is approved on
  the AWS account, the model identifier flips and Claude becomes the
  live LLM.

## Q&A prep — likely questions and tight answers

| Q | A |
|---|---|
| Why Step Functions, not Lambda chaining? | 15-min limit on a single Lambda; Step Functions externalizes retries, supports parallel Map natively, gives a visual exec graph. |
| Why DynamoDB over Postgres? | Access patterns are narrow; PAY_PER_REQUEST means zero idle cost; single-table design is canonical. |
| How do you handle Bedrock failures? | Per-state retries with exponential backoff in Step Functions; on final failure, MarkFailed updates the DDB job to status="failed" with cause. |
| Cost at 1000 summaries/month? | ~$200 dominated by Bedrock tokens. Idle remains $0. |
| Why Qwen and not Claude? | Anthropic use-case form is pending on our AWS account. Bedrock helper supports both formats; switching is one env var. |
| How do you prevent abuse? | Per-user quota stored on the Cognito profile, atomic decrement, refunded on dedup hits. AWS Budgets alarm at $50/month as a safety net. |
| Multi-AZ? Multi-region? | Multi-AZ via every managed service we use. Multi-region DR is documented as future work; out of scope per the original proposal. |
| What's the data pipeline? | SQS → Step Functions Map(fan-out)/Reduce(fan-in) over chunks stored in S3. State payloads stay under 256 KB by passing only S3 keys. |
